# Working Effectively with Legacy Code 读书笔记

## 1. 作者要解决的核心问题
Michael Feathers关注“**如何在缺乏测试的遗留系统中安全地修改代码**”。核心问题是：现实世界的大量系统缺乏可测性与结构化设计，直接修改风险高。书的贡献在于提供具体策略，让团队在高风险环境中逐步建立可测性与可维护性。

## 2. 核心论点（可反驳 + 隐含假设）
1. **遗留代码的本质是“缺少测试的代码”**。假设：测试是改动安全的必要前提。
2. **修改前必须先建立“安全点”**。可反驳点：在紧急修复中，时间可能不足以建立安全点。
3. **应通过“缝合点”隔离依赖**。隐含前提：代码结构允许引入抽象或接口。
4. **小步变更降低风险**。可反驳点：某些架构级问题需要大规模改动。
5. **重构与测试应交替推进**。假设：团队有足够工程投入。

## 3. 关键概念卡片（系统内关系）
- **遗留代码（上层概念）**：缺乏测试保护的代码。
- **缝合点（中层机制）**：通过接口或封装打破依赖，提高可测性。
- **特征测试（中层机制）**：锁定现有行为以避免无意改变。
- **安全点（下层实践）**：确保改动可以被验证与回退。
- **渐进式重构（上层概念）**：在不停止交付的情况下逐步改进结构。

## 4. 机制与结构化框架
- **因果链**：建立测试 → 提高改动安全性 → 增加结构改进空间 → 降低长期维护成本。
- **缝合点策略**：在边界引入隔离 → 可注入依赖 → 可测试性提升。
- **特征测试价值**：先锁定现有行为，再进行优化或修复。

## 5. 与同类书的差异
- 与《Refactoring》相比，本书面对“没有测试的现实”，更强调可测性建立。
- 与《Clean Code》相比，关注“修复与演进”而非“预防性质量”。
- 与《The Pragmatic Programmer》相比，更偏具体遗留系统策略。

## 6. 可迁移的原则
1. **安全性优先于优化**。适用于所有生产系统。
2. **建立最小可测试单元是改动前提**。适用于长期维护系统。
3. **小步演进比大重写更可控**。跨行业适用。

## 7. 实践路径
- **前提**：系统持续运行且不能停止交付。
- **路径**：特征测试 → 缝合点隔离 → 局部重构 → 新功能开发。
- **边界**：若系统已接近不可维护，可能需要并行重写策略。

## 8. 反驳与局限
- **时代背景限制**：对单体系统较多案例，分布式系统需扩展策略。
- **创业公司 vs 大公司**：创业公司难以投入足够时间修复遗留系统；大公司更需要此方法。
- **争议点**：特征测试可能固化错误行为，导致技术债延续。

## 9. 行业贡献与验证
- **贡献**：提供在遗留系统中可执行的工程策略，影响持续交付与重构实践。
- **被验证**：缝合点与特征测试成为遗留系统改进的标准方法。
- **争议**：对复杂分布式系统的适配性需要进一步扩展。
