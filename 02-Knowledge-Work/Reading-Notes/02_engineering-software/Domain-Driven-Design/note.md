# Domain-Driven Design 读书笔记

## 1. 作者要解决的核心问题
Eric Evans关注“**如何在复杂业务系统中建立可持续演进的模型与架构**”。核心问题是：业务复杂性会吞噬技术架构，导致系统无法适应变化。书的贡献在于强调“以领域为中心”，把业务语言与技术模型对齐。

## 2. 核心论点（可反驳 + 隐含假设）
1. **统一语言是复杂系统协作的基础**。假设：业务与技术团队能持续沟通并达成一致。
2. **领域模型应驱动架构设计**。可反驳点：在性能或基础设施主导系统中，领域模型可能被弱化。
3. **边界上下文是系统分解的关键**。隐含前提：领域可被清晰划分。
4. **领域专家必须参与设计过程**。假设：领域专家可参与并投入时间。
5. **复杂系统需要战略层设计而非仅战术模式**。可反驳点：在简单业务中DDD成本可能过高。

## 3. 关键概念卡片（系统内关系）
- **领域模型（上层概念）**：业务逻辑的核心表达。
- **统一语言（中层机制）**：业务与技术共享的语义体系。
- **边界上下文（中层机制）**：领域划分的边界，用于隔离模型。
- **聚合（下层实践）**：一致性边界内的对象集合。
- **上下文映射（下层实践）**：跨边界协作方式与协议。

## 4. 机制与结构化框架
- **因果链**：统一语言 → 模型一致 → 需求变更可控 → 系统可演进。
- **边界上下文**：将复杂度拆分成可管理单元，降低系统耦合。
- **战略设计**：先确定领域边界与协作方式，再做战术建模。

## 5. 与同类书的差异
- 与《Clean Code》相比，DDD关注宏观架构与领域建模，而非代码风格。
- 与《Designing Data-Intensive Applications》相比，DDD强调业务模型，而非基础设施权衡。
- 与《Refactoring》相比，本书更关注设计前期的建模方法。

## 6. 可迁移的原则
1. **业务语言与系统模型必须对齐**。适用于复杂业务系统。
2. **边界清晰是降低复杂度的核心**。跨行业适用。
3. **战略设计优先于战术技巧**。适用于多团队、多系统协作。

## 7. 实践路径
- **前提**：业务复杂度高且变化频繁。
- **路径**：领域知识收集 → 统一语言 → 边界上下文划分 → 模型落地 → 持续调整。
- **边界**：在简单CRUD系统中，DDD可能过度设计。

## 8. 反驳与局限
- **时代背景限制**：书中案例多基于传统企业，现代微服务需扩展实践。
- **创业公司 vs 大公司**：创业公司资源有限，可能先用轻量模型；大公司更需要DDD。
- **争议点**：实践成本高且对团队成熟度要求高。

## 9. 行业贡献与验证
- **贡献**：建立领域建模的系统方法论，影响微服务与架构设计。
- **被验证**：边界上下文与统一语言已成为复杂系统设计标准。
- **争议**：在业务稳定、复杂度低的场景投入过高。
