# Clean Code（代码整洁之道）读书笔记

## 核心论点（Top 7）
1. **代码是可持续演进的主要载体，整洁代码直接影响团队生产力与系统可靠性**
   - 作者判断：代码是可持续演进的主要载体，整洁代码直接影响团队生产力与系统可靠性。
   - 隐含前提：代码会被反复阅读与修改，阅读成本远高于编写成本；
   - 与同类观点差异：“能跑就行”的观念不同，作者强调可读性是长期成本的核心。
   - 应用校准：在实践中应明确证据来源与适用范围，否则容易被简化为口号或流程装饰。
2. **函数应小而单一职责，以降低认知负担与变化传播**
   - 作者判断：函数应小而单一职责，以降低认知负担与变化传播。
   - 隐含前提：人类理解能力有限，复杂函数会放大缺陷；
   - 与同类观点差异：“长函数提高效率”的误解不同，作者强调拆分带来的可维护性。
   - 应用校准：在实践中应明确证据来源与适用范围，否则容易被简化为口号或流程装饰。需要结合组织能力与市场阶段做校准，否则会产生系统性错配与资源浪费。

## 方法 / 框架
1. **函数分解法**：逻辑成立于降低认知负荷与提高可测试性。失效条件是过度拆分导致逻辑碎片化或性能敏感场景不适用。
2. **重构与测试协同**：逻辑成立于测试提供回归安全网，重构改善结构。失效条件是测试覆盖不足或测试质量低导致错误隐藏。
3. **命名驱动设计**：通过命名明确边界与职责，逻辑成立于命名是沟通核心。失效条件是领域知识不足导致命名偏离业务语义。

## 反驳与局限
1. **时代局限**：书中部分建议基于面向对象语言与类库设计，对函数式或数据驱动架构的适配需要调整。
2. **规模假设**：作者假设团队愿意投入持续重构，但在高压交付环境下可能难以执行。
3. **被后续实践挑战**：部分实践指出过度强调细粒度规则会导致“教条化”，需要结合上下文做取舍。

## 跨书对比（与《Refactoring（重构）》）
《代码整洁之道》强调编码习惯与可读性，《重构》强调在不改变外部行为的前提下改进结构。冲突点在于：整洁代码更强调前置约束，而重构强调后期补救与演进。适用场景差异是：新代码开发可优先遵循整洁原则；遗留系统更需要重构方法论支撑。
