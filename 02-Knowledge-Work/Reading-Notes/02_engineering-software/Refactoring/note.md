# Refactoring 读书笔记

## 1. 作者要解决的核心问题
Martin Fowler关注“**如何在不改变外部行为的前提下持续改进代码结构**”。核心问题是：软件系统必然演进，若不重构，结构会退化导致交付速度下降。书的贡献在于系统化定义“重构”的概念与流程。

## 2. 核心论点（可反驳 + 隐含假设）
1. **重构是日常开发的一部分，而不是专门阶段**。假设：团队有测试保障和时间预算。
2. **结构改进能直接提升交付效率**。可反驳点：短期内重构可能降低交付速度。
3. **小步重构比大规模重写更安全**。隐含前提：代码有足够的可测性。
4. **坏味道是重构的信号**。可反驳点：某些复杂性来自业务本身，非设计问题。
5. **自动化测试是重构的前置条件**。在缺乏测试的遗留系统中难以实施。

## 3. 关键概念卡片（系统内关系）
- **重构（上层概念）**：不改变外部行为的内部结构改进。
- **坏味道（中层机制）**：提示潜在结构问题的代码迹象。
- **小步变更（中层机制）**：降低风险与回退成本。
- **回归测试（下层实践）**：保证行为一致性的安全网。
- **技术债（上层概念）**：重构是偿还技术债的主要手段。

## 4. 机制与结构化框架
- **因果链**：坏味道识别 → 小步重构 → 结构改善 → 交付效率提升。
- **重构节奏**：与功能开发并行，避免“先修后做”的大停工。
- **风险控制**：自动化测试与版本控制降低重构风险。

## 5. 与同类书的差异
- 与《Clean Code》相比，本书强调结构改进流程而非编码规则。
- 与《Working Effectively with Legacy Code》相比，更适用于有测试基础的系统。
- 与《The Pragmatic Programmer》相比，更具操作层面的重构细节。

## 6. 可迁移的原则
1. **持续重构是保持系统可演进的关键**。跨行业适用。
2. **重构必须小步可验证**。适用于任何有持续交付需求的团队。
3. **坏味道提供诊断线索**。适用于代码审查与技术债管理。

## 7. 实践路径
- **前提**：具备一定自动化测试覆盖。
- **路径**：识别坏味道 → 选择合适重构手法 → 小步执行 → 回归测试。
- **边界**：缺乏测试的系统需先建立隔离测试或端到端测试。

## 8. 反驳与局限
- **时代背景限制**：初版以面向对象语言为主，函数式或动态语言需调整手法。
- **创业公司 vs 大公司**：创业公司可能推迟重构以换速度；大公司更依赖重构维护。
- **争议点**：重构投入与业务收益的衡量常被高估或低估。

## 9. 行业贡献与验证
- **贡献**：确立“重构”概念及术语，成为工程实践核心。
- **被验证**：持续重构与测试结合已是主流工程文化。
- **争议**：在高压交付环境中，重构往往被边缘化。
